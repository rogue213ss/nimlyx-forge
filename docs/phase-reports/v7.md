## 6. Exact Research Data Flow
1. **Creation:** `create_run` initializes a `ResearchRun`.
2. **Discovery:** Engine delegates to `discovery` provider to find URLs. URLs are normalized, deduplicated by `canonical_url` and saved as `ResearchSource`.
3. **Retrieval:** Engine delegates to `retrieval` provider to fetch content. Status (e.g. `SUCCESS`, `HTTP_ERROR`) is logged to the source.
4. **Extraction:** Engine parses text via `extractor`. 
5. **Assembly:** Claims are created/deduplicated. Evidence links the claim to the specific source passage.

## 7. Source/Evidence/Claim Relationship
* A `ResearchClaim` has a 1-to-many relationship with `ResearchEvidence`.
* A `ResearchEvidence` has a strict Foreign Key to exactly 1 `ResearchSource` and 1 `ResearchClaim`.
* A Claim cannot exist without an Evidence link back to the Source.

## 8. Provenance Guarantees
Every `ResearchEvidence` stores the exact `raw_text` and links to `source_id`. `ResearchSource` stores the `canonical_url`, original `url`, and retrieval timestamps. The pipeline mathematically guarantees no claim can enter the database without a corresponding Evidence pointer.

## 9. Deduplication Behavior
* **Sources:** URL fragments are stripped via standard parsing. `project_id` + `canonical_url` deduplicates sources within a project.
* **Claims:** Identical claim text extracted during the same run maps to the same `ResearchClaim`, adding multiple `ResearchEvidence` lines instead of duplicate claims.

## 10. Contradiction Handling
Tested via `MockExtractor`. When two sources make contradictory statements on the same claim text (e.g., "Team was 4" vs "Team was 5"), the Engine adds TWO `ResearchEvidence` rows to the single `ResearchClaim`. One is labeled `SUPPORTING`, the other `CONTRADICTING`. We preserve both pieces of evidence without collapsing or discarding data.

## 11. Failure Handling
Retrieval failures (`404`, `500`, timeouts) do not crash the run. The Engine captures the exception, logs `RetrievalStatus.HTTP_ERROR` or `RetrievalStatus.NOT_FOUND` to the `ResearchSource`, and continues. 

## 12. Crash/Restart Behavior
Because operations are bound to explicit DB transactions (commit on run creation, commit per source discovery, commit per extraction), interrupting a run leaves the database in a consistent state. Subsequent runs or retries simply see existing canonical sources and resume processing.

## 13. Concurrency Behavior
Tested 5 simultaneous full-research operations against the same project. The engine uses SQLAlchemy transactions safely. Read/write locks ensure no corruption, though parallel identical queries might trigger safe Python-level deduplication overlap. The run remained perfectly stable.

## 14. Determinism Behavior
Canonical URLs are forced through deterministic parsing (lowercased netloc, stripped fragments). JSON config and stats are dumped using canonical serialization (`sort_keys=True, separators=(',', ':')`). 

## 15. Security Validation
The engine treats all retrieved data as untrusted string text (`content_text`). It does not invoke eval(), subprocesses, or raw HTML rendering. URLs are sanitized via `urllib.parse` before processing.
