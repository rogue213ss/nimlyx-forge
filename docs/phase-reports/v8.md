The V8 Story Builder pipeline has been fully implemented, integrated, and validated. ## 1. ARCHITECTURE & COMPONENTS

### 1.1 New SQLAlchemy Models (Schema)
* **`StoryRun`**: The top-level execution context preserving configuration, status, and analytical metrics.
* **`StoryEvent`**: Connects directly to `ResearchClaim`, mapping explicitly to a timeline via `DatePrecision`.
* **`StoryBeat`**: Mapped to Events, this represents the narrative significance via `NarrativeRole` (HOOK, SETUP, TURNING_POINT, CONCLUSION) and `emotional_state` metadata.
* **`StoryAct`**: Groups `StoryBeats` into logical progressions (e.g. "Act 1: The Promise", "Act 2: The Reality").

### 1.2 Extensions to V1–V7.3 Models
Rather than duplicating models, the existing `Scene`, `NarrationSegment`, and `VisualIntent` were securely adapted via `ALTER TABLE`:
* `Scene` now tracks `story_run_id`, `story_beat_id`, and `act_id`.
* `NarrationSegment` distinguishes rough brief metadata (purpose, `must_communicate`, `must_not_claim`, `supporting_claims`) from final script prose via a new `is_brief` flag.
* SQLite `ALTER` syntax incompatibilities for Foreign Keys and Enum modification were bypassed programmatically via a clean DB rebuild (as required for dev migrations).

## 2. PIPELINE BEHAVIOR

### 2.1 Claim Selection
`StoryBuilder._select_claims` implements a rigid evaluation heuristic:
* **Excludes**: `REJECTED`, `LOW_QUALITY`.
* **Avoids**: `CONFLICTED` claims are deterministically bypassed to avoid hallucinating a resolution.
* **Scoring Rules**: Claims earn selection significance based on `STORY_READY` status, corroboration levels (Tier 1/2), and regex-matched temporal/scale indicators (dates, sales numbers, budgets).

### 2.2 Timeline Reconstruction
The pipeline extracts explicit temporal contexts from unstructured text without fabricating data.
Dates are preserved with precision constraints (`EXACT_DATE`, `MONTH`, `YEAR`, `RELATIVE`, `UNKNOWN`), preserving statements like "years later".

### 2.3 Narrative Arc
Events are sorted chronologically and placed onto a structured 3-act pacing logic. Beats are dynamically assigned roles:
1. **Act 1**: HOOK -> SETUP
2. **Act 2**: RISING TENSION
3. **Act 3**: REFLECTION -> CONCLUSION
